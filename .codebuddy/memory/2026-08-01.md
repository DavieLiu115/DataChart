## 需求 6：修复导出图片 fillRect 起点错误（黑色背景 + 居中问题）

### 用户反馈
- 上一轮修复后，清晰度 OK，但**导出图仍有黑色背景**（顶部/底部/左/右有黑色条）
- **图片没居中**（黑色条宽窄不对称）

### 根因（第二版 fillRect 仍错误）
上一轮我把 fillRect 改为 `fillRect(0, 0, width, height)`，以为这是"用户坐标 (0, 0) 到 (width, height)"。但忽略了：
- g2d transform 链 = `scale(s, s) ∘ translate(-minX, -minY)`
- T(P) = (P - (minX, minY)) * s
- 用户坐标 (0, 0) 映射到设备 (-minX*s, -minY*s)——**不是** (0, 0)！
- 用户坐标 (width, height) 映射到设备 ((width-minX)*s, (height-minY)*s)——**比** (width*s, height*s) **小**

结果：fillRect 在设备上只覆盖 [0, (width-minX)*s] x [0, (height-minY)*s]，**右/下**各缺 minX*s / minY*s 像素 = BufferedImage 默认 0x000000 黑色透出。

### 修复
**fillRect 必须用 exportArea 的画板起点 (minX, minY) 作为起点**：
- `fillRect((int) minX, (int) minY, width, height)`
- T(minX, minY) = (0, 0) ✓
- T(minX+width, minY+height) = (width*s, height*s) ✓
- 完美覆盖整个 BufferedImage

### 居中问题（额外修复）
原 `calculateTotalBounds` 用 `Rectangle(minX-40, minY-40, w+80, h+80)`：
- 上下 padding 是 40 对称 ✓
- 但**左右 padding 不对称**（minX=140 时左边 padding=180，右边=40）
- **改用对称 padding**：以"卡片合并中心"为中心，加 padding：
  ```java
  double centerX = (minX + maxX) / 2.0;
  double centerY = (minY + maxY) / 2.0;
  double halfW = (maxX - minX) / 2.0 + padding;
  double halfH = (maxY - minY) / 2.0 + padding;
  return Rectangle(centerX - halfW, centerY - halfH, halfW*2, halfH*2);
  ```
  - 这种写法的画板坐标与原 `minX-40` **完全一致**（数学上等价），但语义清晰：四面对称 padding，exportArea 中心 = 卡片合并中心
  - focusView() 用的不是 calculateTotalBounds（自己重新算 min/max），不受影响

### 关键教训
- **Java 2D transform 链是"前乘"（prepend）**：`g2d.translate(tx, ty)` 之后 `g2d.scale(s, s)`，最终 T = scale ∘ translate，不是 translate ∘ scale
- **fillRect 是用户坐标，不是设备坐标**：`fillRect(x, y, w, h)` 中 (x, y) 是 g2d 用户坐标，必须先应用 inverse transform 才能映射到设备
- **检查 transform 起点**：始终算 T(userPoint) = devicePoint，看起点是否对应 BufferedImage (0, 0)
- **Bounding box 对称 vs 最小覆盖**：导出范围应该是"内容 + 对称 padding"而不是"min - padding"，否则会偏

## 需求 8：fillRect 反复修复但仍显示黑色（最终方案）

### 现象
- 之前几轮（需求 4、6）反复修改 `fillRect` 起点（`fillRect(0, 0, w, h)` / `fillRect(minX, minY, w, h)`），但用户每次都说"图片还是不行啊，仔细检查一下"
- 仔细看 user 图：左侧 / 底部有大块黑色 + 网格密集

### 根因（最终推断）
- **fillRect 之前用 transform 链计算**：`g2d.translate(-minX, -minY) + g2d.scale(s, s)` 后 `fillRect((int) minX, (int) minY, w, h)`。
  数学上 T(minX, minY) = (0, 0), T(minX+width, minY+height) = (width*s, height*s) 应该完美覆盖，但**实际效果仍有黑色透出**（可能是 drawGrid / drawCard 之前某些初始化 / antialiasing 副作用）
- **drawGrid 用 `getBounds()`**（KanbanBoard JPanel 屏幕大小，~2000x1500），画网格范围远超 exportArea，但**在 BufferedImage 内（clip 限制）**画 0.5f 灰色密集网格
- **drawCard 阴影**：`Color(0, 0, 0, 30)`（12% 透明黑色），在白底上几乎不可见，但**叠加在 fillRect 没填到的黑色背景上**看起来更黑

### 最终修复
- **paintForExport 重构：先 fillRect 清屏，再 apply transform 画其他内容**
  - 第一步：`g2d.setColor + g2d.fillRect(0, 0, deviceW, deviceH)` 用设备坐标 (0, 0) 完整覆盖整个 BufferedImage
  - 第二步：`g2d.translate + g2d.scale` 应用 transform
  - 背景 fillRect 走设备坐标，**不依赖 transform 数学计算**，确保 100% 覆盖
- **fillRect + clearRect 双保险**：
  - `g2d.setColor + g2d.fillRect(0, 0, deviceW, deviceH)` 用 setColor 颜色
  - `g2d.setBackground + g2d.clearRect(0, 0, deviceW, deviceH)` 用 setBackground 颜色
  - 两种方式互为冗余，确保任何一种生效都能覆盖
- **paintForExport 签名增加 deviceW/deviceH 参数**：
  - `paintForExport(g2d, exportArea, dark, scale, deviceW, deviceH)`
  - PDF 调用：`deviceW = exportArea.width, deviceH = exportArea.height`（scale=1.0）
  - Image 调用：`deviceW = targetW = exportArea.width*scale, deviceH = targetH = exportArea.height*scale`
  - 旧 3 参数重载保留为兼容性 wrapper，调用 `(g2d, exportArea, dark, 1.0, exportArea.width, exportArea.height)`

### 关键教训
- **fillRect 起点用设备坐标 (0, 0) 比 transform 链更可靠**：Java 2D 的 transform 数学计算虽然对，但实际渲染中可能有各种 side effect（antialiasing, clip, 颜色混合模式），用设备坐标 (0, 0) 画最简单
- **fillRect + clearRect 双保险**：两种方式等价但互为冗余，setBackground 颜色可能被 IDE 主题修改，setColor 颜色固定
- **paintForExport 与 g2d 类型解耦**：PDF 和 Image 用不同 transform 行为，传入 deviceW/deviceH 让 paintForExport 知道实际"目标区域"大小

## 需求 12：修复"导出图片右边没显示完"（卡片宽度固定 280px 不够）

### 用户反馈

- sys_job 有 19 个字段，最长字段 `invoke_target : varchar(500) /* 调用目标字符串 */` 总宽 ~500px

### 修复方案

1. `KanbanCard.computeRequiredWidth(TableInfo)`（静态方法）：
   - 离屏 BufferedImage(1,1) 拿 FontMetrics，真实测量（不靠 char.length * 7 估算）
   - 遍历所有列：`padding + 20 (图标) + colName + " : " + colType + 6 + "/* " + comment + " */" + padding`

### 关键设计

- **最小宽度 280 不变**：字段少（3-5 个）的表不会因修复而变宽，保持视觉一致性
- **用户主动加宽保留**：explicitWidth > required 时用 explicitWidth（适配"用户手动拖宽"场景）
