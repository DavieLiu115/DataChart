## 需求 19：连线起点/终点加水平引出线 + 贝塞尔曲线

### 用户反馈
- 多对多关系中，起点和终点 Y 不对齐时，连线在靠近卡片处是斜的，看起来很别扭
- 期望：挨着起点和终点的一段改为始终水平的，引出一点之后再用曲线过渡，视觉更顺

### 实现
- 修改 `Connection.draw()`，连线绘制由"一条 CubicCurve"改为"水平引出线 + CubicCurve + 水平引出线"三段：
  1. 起点水平直线：`sourcePoint` → `(sourcePoint.x + dirSign*leadLen, sourcePoint.y)`
  2. 中间 CubicCurve：起点 `(leadStartX, leadStartY)`，终点 `(leadEndX, leadEndY)`，控制点 Y 与各自端点 Y 相同 → 曲线两端水平进入/水平离开
  3. 终点水平直线：`(targetPoint.x - dirSign*leadLen, targetPoint.y)` → `targetPoint`
- `leadLen = clamp(|dx|/3, LEAD_MIN=24, LEAD_MAX=60)` 画板坐标（让引出线长度与卡片间距成比例，但不会过长）
- `dirSign = sign(dx)`：起点在终点右侧（右→左连线）时引出线方向正确

### 副作用（自动变好）
- 端点形状通过 `(otherEnd - endpoint)` 算方向，最后一段水平 → "1"端竖线真正竖直、"多"端三叉真正水平打开

### 关键设计
- **draw order**：起点引出线 → 曲线 → 终点引出线，避免覆盖
- **dx 为负时方向反转**：用 `dirSign` 一次解决，不写两套
- **clamp 上下限**：水平距离很小时（卡片挨着）取 LEAD_MIN，距离很大时取 LEAD_MAX，避免曲线部分消失或引出线过长

## 需求 20：连线端点形状改为开口椭圆（不再区分 1/多）

### 用户反馈
- 需求 19 改完之后，"1"端竖线竖直了，但**"多"端三叉（crow's foot）还是斜的**，整体视觉还是歪
- 期望：参考截图，两端都画一个**开口椭圆**（"环"/"眼"形状），更简洁更一致

### 实现
- `drawEndpointShape` 重写：不再根据 `relationType` 区分两端形状，两端统一画开口椭圆
  - 椭圆中心在端点处
  - 长轴垂直于连线方向 = 竖直（因为引出线始终水平，所以方向 = 竖直）
  - 短轴沿连线方向 = 水平
  - 长轴半长 `size * 0.7`，短轴半长 `size * 0.25`
  - `size = max(8, strokeWidth * 4.5)` 随线宽缩放
- 方法签名简化：去掉 `otherEnd` 和 `isSource` 参数（不再需要方向和源/目标判断）
- `RelationType` 字段保留（持久化到 JSON 不变），但渲染时不再使用

### 关键设计
- **方向对齐**：开口椭圆长轴竖直，与端点前的水平引出线形成"垂直穿入"效果，视觉上一致
- **不再区分 1/多**：用户反馈参考图中两端形状相同，简化 ER 标注差异性，专注视觉一致性
- **stroke 比线略细**：`max(1.2f, strokeWidth * 0.85f)`，让环看起来精致不喧宾夺主
- **Ellipse2D.Double 几何**：`x = cx - halfMinor, y = cy - halfMajor, w = 2*halfMinor, h = 2*halfMajor`

### 教训
- **多轮迭代要持续定位视觉问题**：需求 19 修了曲线方向，但端点形状的方向依赖连线方向（`(otherEnd - endpoint)`），曲线方向 ≠ 引出线方向；三叉仍按原始连线方向算就还是斜的——只有把端点形状完全改造成与"水平引出线"对齐的形状（开口椭圆）才能彻底解决
- **简化 > 区分**：用户既然要"两端都是椭圆"，就放弃 "1/多" 区分，避免维护两套渲染分支

## 需求 21：端点椭圆放大 + 向外偏移（更醒目）

### 用户反馈
- 上一轮画的椭圆**有一半被卡片遮住**，看起来不明显
- 期望：椭圆整体"出来一点"，更醒目

### 实现
- 椭圆尺寸放大：
  - 长轴半长 `size * 0.7` → `size * 0.8`（垂直方向）
  - 短轴半长 `size * 0.25` → `size * 0.35`（水平方向）
- 椭圆中心**向外偏移 `ELLIPSE_OFFSET = 6.0` 像素**：
  - 起点（sourcePoint 在源卡右边）→ 向右偏移（+X）
  - 终点（targetPoint 在目标卡左边）→ 向左偏移（-X）
  - 偏移方向**与连接方向无关**（源/目标点的几何位置就决定"外侧"）

### 关键设计
- **偏移方向不由 dirSign 决定**：之前误以为偏移方向需要 dirSign，但 sourcePoint 永远在源卡右边（getRowRight），targetPoint 永远在目标卡左边（getRowLeft），所以外侧方向固定
- **偏移量大小**：6 像素，画板坐标；用户用中等缩放看时大约 12-18 视觉像素，明显但不夸张
- **尺寸 + 偏移双管齐下**：仅放大一半仍被卡片挡，仅偏移一半还在卡片内；两个一起做才完全外露

## 需求 22：行高亮背景下文字色自适应（深色模式白字看不清）

### 用户反馈
- 深色主题下，选中行（连线占用的浅蓝/粉色背景）文字看不清
- 截图：`show_in_query` 行背景是浅蓝色，列名字体像深蓝色但与浅蓝背景几乎融为一体

### 根因
- 行高亮背景都是**亮色**（连线占用 = 线色本身，多为浅蓝/粉色/淡紫；搜索 = 淡黄/深黄；用户选中 = 橙色）
- 文字色硬编码 = 主题默认色（深色主题 = 白字 `#FFFFFF`，浅色主题 = 黑字 `#222222`）
- **亮背景 + 白字 = 对比度差**（深色主题特有的问题）
- 浅色主题下：亮背景 + 黑字 = 对比度 OK，所以以前没暴露

### 修复方案
- 新增 `KanbanCard.isLightColor(Color)`（静态，YIQ 公式，与 `BoardExportUtil.isDarkTheme` 反义）
- `drawTableCard` 的行循环里，对**每一行**计算自适应文字色：
  - `adaptDarkText = highlightColor != null && isLightColor(highlightColor)`
  - 亮背景 → 文字用深色：
    - 列名 `#222222`
    - 类型 `#0E5A8E`（深蓝，比主题默认的 `#2470B0` 更深，避免与浅背景对比不够）
    - 冒号 `#666666`
    - 注释 `#555555`
  - 暗背景或无高亮 → 维持主题默认色（深色主题白字，浅色主题黑字）
- **影响范围**：仅表格卡片 `drawTableCard` 的列名/类型/冒号/注释；图标颜色不变；表头/卡片标题/边框不受影响

### 关键设计
- **每行独立判断**：不同行可有不同高亮背景（连线占用的颜色不同），所以文字色判断必须在循环内，不能在循环外
- **YIQ 公式沿用 `BoardExportUtil.isDarkTheme`**：保持一致，避免维护多套亮度公式
- **不修改 `drawChartCard`**：图表卡片没有行高亮，无需修改
- **图标颜色不改**：图标用主题自适应色（`resolveColumnIcon`），与背景无关

### 教训
- **深色主题的特殊问题**：浅色主题下"白底黑字"足够对比，但深色主题下任何"亮背景"（浅蓝/淡黄/橙）都会让默认白字对比度变差
- **图标 vs 文字区别处理**：图标有自己主题适配（`resolveColumnIcon`），文字没有——所以需要单独加文字自适应逻辑
- **优先级判断与文字色无关**：用户选中 > 搜索焦点 > 搜索命中 > 连线占用（背景色优先级）；但**文字色**只判断"背景亮不亮"，与背景色来源无关
- **YIQ 与主题判断对称**：复用 `BoardExportUtil.isDarkTheme` 的相反公式，避免定义两套亮度标准
