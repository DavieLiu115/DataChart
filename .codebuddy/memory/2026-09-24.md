## 属性键高亮：键名与字符串值同色 → 补 `DataChartJsonKeyAnnotator`
用户对比：之前（自研 Text Tab 用 `JsonFileType` 的 LightVirtualFile）键名是紫色、值绿色；现在键名是绿色（与值同色）。

- 根因：JSON 的**属性键颜色不是 token 级高亮**，而是
  `com.intellij.json.highlighting.JsonRainbowVisitor` 调 `JSON_PROPERTY_KEY` 标出来的
  （`highlighting` 包里没有 Annotator；`JSON_PROPERTY_KEY` 只被 `JsonSyntaxHighlighterFactory` / `JsonRainbowVisitor` /
  `JsonLiteralAnnotator` / `JsonColorsPage` 引用）。`JsonRainbowVisitor` **注册在 `language="JSON"`**、且是 **final 类**，
  `suitableForFile` 会拒绝非 JSON 语言 → 借 syntaxHighlighterFactory 只借到 token 色（字符串/关键字/数字）。
- 解法：新增 `com.wd.editor.DataChartJsonKeyAnnotator`（`<annotator language="dataChart">`）：
  文本扫描找"字符串后紧跟冒号（中间只允许空白）"的键，"字符串右引号后出现其它非空白字符就作废"（避免误判数组元素），
  标成 `JsonSyntaxHighlighterFactory.JSON_PROPERTY_KEY`（颜色跟随主题 / Color Scheme 的 JSON 配置）。
  ⚠️ annotator 按 PSI 元素逐个调用 → 扫描必须限定 `element instanceof PsiFile`，否则整文件被重复扫 N 遍。
- 兜底：若 annotator 在"无 ParserDefinition 的自定义语言"下不运行，再给 dataChart 注册
  `<lang.parserDefinition language="dataChart" implementationClass="com.intellij.json.JsonParserDefinition"/>`（JSON 的 parser 是语言无关实现）。
- `./gradlew compileJava` 通过、0 警告。

## 键色复盘（用户："还是这样啊，之前那个高亮是怎么实现的"）
- **之前那版为什么高亮完美**：自研 Text Tab 用的是 `LightVirtualFile(name + ".json", JsonFileType.INSTANCE, text)`
  → 那个编辑器的**文件语言就是 JSON**，JSON 的全套机制（PSI、高亮访客、annotator、inspection）都生效，
  所以键名是紫的。
- 现在（平台文本编辑器 + 自定义语言 dataChart）：`syntaxHighlighterFactory` 只能借到 **token 色**；
  键色 `JSON_PROPERTY_KEY` **不在 `MyHighlighter` 的 token 映射表里**（映射表里 `IDENTIFIER → JSON_IDENTIFIER`、
  `DOUBLE_QUOTED_STRING → JSON_STRING`），它只被 `JsonRainbowVisitor`（PSI 层）等引用
  → 想"改 lexer token 类型"骗过键色是行不通的（会得到 JSON_IDENTIFIER 色）。
- 结论：键色必须走 PSI 层。已做两件事：
  1. `DataChartJsonKeyAnnotator`（文本扫描"字符串后紧跟冒号"的键 → 标 `JSON_PROPERTY_KEY`）；
  2. **annotator 在 plain PSI 下不会被 daemon 调用** → 新增 `DataChartJsonParserDefinition`
     （继承 `JsonParserDefinition`，覆盖 `createFile` 用 `new JsonFileImpl(viewProvider, DataChart.INSTANCE_C)`，
     父类硬编码 `JsonLanguage.INSTANCE` 会导致 PSI 语言与 FileType 语言不一致）+ plugin.xml 注册 `<lang.parserDefinition>`。
- **Tab 顺序的硬事实**（反编译核实）：`PLACE_BEFORE/AFTER_DEFAULT_EDITOR` **平台没有任何代码读取**
  （全 jar 扫描只有 `DiffPatchFileEditorProvider` / `PerspectiveFileEditorProvider` 声明使用它，没有处理者），
  `order` 属性实测无效，平台 text provider `order="first"` 且 provider 列表走协程并发创建
  → **只要用平台文本编辑器，它就会排在自定义 editor 前面**。要 100% 控制顺序只能"一个 FileEditor 内部两个页签"。
- `./gradlew compileJava` 通过、0 警告。

### 拖线时起点行背景太黑 → 拆出独立色（用户反馈）

  一个色值不可能同时满足"细线要够深"与"行背景要够浅"。

- 选色基准：卡片底色 `KanbanCard.BG_LIGHT=#FFFFFF` / `BG_DARK=#3C3F41`。
- 文档：追加到 DEVELOPMENT_GUIDE §34（含通用规律：语义色兼作"细线 + 整行背景"时必须拆两个常量）。

### 预览色与建线后的颜色不一致（用户："连过去是绿的，一松手变成蓝色了"）
上一版只修了"起点行太黑"，但预览仍是固定色（起点浅灰蓝 / 目标淡绿 / 线深灰），
松手后整条线与两端行背景都变成 palette 色 → 视觉上"跳色"。

- 修法：新增 `peekNextConnectionColor()` = `CONNECTION_COLOR_PALETTE[connectionColorIndex % len]`，
  预览线 / 起点行 / 目标行**三处统一用它**。
  关键依据：`connectionColorIndex` 只在 `addConnection` 里自增，拖拽期间不变 → 预取的就是最终色。
  因此既做到"预览 = 结果"，又保住"连一次换一个颜色"（2026-08-04 用户要求）。
- 三个旧预览常量（`CONNECTION_PREVIEW_COLOR` / `CONNECTION_SOURCE_PREVIEW_COLOR` / `CONNECTION_TARGET_PREVIEW_COLOR`）
  现在都没人用，保留 + `@SuppressWarnings("unused")` + 注释（要回退就换回去）。
- 已知小差异：预览线 1.6f、建线后 2.4f（颜色已不跳，只是略变粗）。
- 教训：这类"预览态 / 最终态"的配色，只要用户提出"一致"，就该用**预测最终值**的方式解决，
  而不是把最终态改成预览色（后者会破坏"每条连线颜色不同"这类既有约定）。
- 文档：§34 末尾该小节整段重写。`./gradlew compileJava` 通过、0 警告。
